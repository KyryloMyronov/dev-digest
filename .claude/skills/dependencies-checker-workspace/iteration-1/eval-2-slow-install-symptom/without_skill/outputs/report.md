# Чому `pnpm install` в client і `npm install` в mcp сповільнились

Дивився реально на диск (`du -sh`), реальні `package.json`/lockfiles, і грепав
`src/` перш ніж щось називати "невикористаним". Головний висновок наперед: у
`client` все важке, але легітимне і використовується; у **`mcp` знайшов
реальний баг** — пакет змішав два package-менеджери, і саме це, скоріш за все,
і є причиною "install став помітно довше".

## 1. Розміри node_modules (виміряно `du -sh`)

| Пакет | node_modules |
|---|---|
| client | **623M** |
| server | 234M |
| mcp | **166M** |
| reviewer-core | 78M |
| e2e | 37M |

## 2. client (623M) — важке, але все реально використовується

Топ за розміром:

| Пакет | Розмір | Використання (grep по `src/`) |
|---|---|---|
| `next` | 152M | фреймворк, звісно використовується |
| `mermaid` | **75M** | `grep "mermaid"` спершу дав 0 — бо імпорт динамічний: `src/components/mermaid-diagram/MermaidDiagram.tsx:36` робить `await import("mermaid")` (lazy, client-only, навмисно, є коментар у файлі чому). Реально рендерить `BlastRadiusCard`. Не мертвий код. |
| `lucide-react` | 36M | Використовується лише в 1 файлі, але це нормально для lucide — пакет фізично містить окремий `.js`/`.d.ts` файл на кожну з ~1500 іконок (для tree-shaking), тому розмір на диску не корелює з тим, що потрапить у бандл. Не bloat, а особливість пакету. |
| `typescript` | 23M | dev, використовується |
| `react-dom` | 7.1M | ok |
| `recharts` | 5.2M | використовується у 2 файлах |
| `zod` | 5.0M | ok |
| `jsdom` | 4.1M | test env |
| `vitest` | 1.9M | test |
| `jszip` | 880K | `src/lib/skill-import.ts` — використовується |
| `react-markdown` + `remark-gfm` | 124K | використовуються (1 файл) |

Все, що заявлено в `client/package.json` (`mermaid`, `lucide-react`,
`recharts`, `jszip`, `react-markdown`, `remark-gfm`, `next-intl`) — насправді
є у стеку за `client/AGENTS.md` і реально імпортується. **Нічого зайвого чи
мертвого в client я не знайшов.** 623M — це просто ціна Next.js + mermaid +
lucide, помножена на те, що `client` не є частиною pnpm workspace (кожен з 5
пакетів має власний, повний `node_modules` — це задокументоване, свідоме
рішення архітектури: "Five standalone packages, NOT a pnpm workspace").

Версії спільних пакетів (`zod`, `typescript`, `vitest`, `@types/node`)
задекларовані з однаковими `^`-діапазонами в усіх 5 пакетах і фактично
резолвляться в однакові версії (`zod@3.25.76`, `typescript@5.9.3`,
`vitest@2.1.9`) — версійного дрейфу між пакетами немає.

## 3. mcp (166M) — знайдено реальну проблему: два package-менеджери в одному пакеті

Це і є найімовірніша причина того, що `npm install` в `mcp` став повільнішим.

Факти (перевірено, не здогадки):

```
mcp/
├── package-lock.json      ← npm lockfile
├── pnpm-lock.yaml         ← pnpm lockfile (!)
├── pnpm-workspace.yaml    ← pnpm workspace config (!)
└── node_modules/
    ├── .package-lock.json         ← маркер, що npm колись тут працював
    └── .pnpm/                      ← маркер, що ЗАРАЗ дерево створене pnpm
        ├── typescript@5.9.3/...
        ├── vitest@2.1.9_.../...
        └── esbuild@0.21.5/, esbuild@0.28.2/   ← дубль (нижче)
```

- `node_modules/typescript`, `node_modules/vitest`, `node_modules/zod` — це
  **symlink'и** в `node_modules/.pnpm/...` (`ls -la` це показав напряму). Це
  структура, яку створює **pnpm**, а не npm.
- Водночас `node_modules/.package-lock.json` (внутрішній маркер npm) теж
  присутній — тобто в якийсь момент тут реально запускали `npm install`.
- Обидва lockfiles (`package-lock.json` і `pnpm-lock.yaml`) **закомічені в
  git** (`git log` показує їх ще з коміту "Lab4 done.", `2ba3303 initial
  commit`) — це не випадковий сміттєвий файл на диску, а стан, який реально
  потрапляє в репозиторій.
- Це прямо суперечить власній конвенції репо (`AGENTS.md`: "Two package
  managers on purpose. server/client use pnpm; reviewer-core/mcp/e2e use
  npm") — `mcp` мав би бути чисто-npm, як `reviewer-core` і `e2e` (перевірив
  обидва — там лежить лише `package-lock.json`, жодного pnpm-файлу).

**Чому це сповільнює саме `npm install`:** зараз реальне дерево на диску
побудоване pnpm-логікою (symlink-и в `.pnpm/`), а `npm install`/`ci` очікує
свою власну "плоску" структуру і звіряється зі своїм внутрішнім
`.package-lock.json`, який тут датований на кілька днів раніше (21 серпня)
за поточні lockfiles (24 серпня) — тобто застарілий і не відповідає тому, що
зараз реально стоїть. У такому стані npm не може зробити швидкий
інкрементальний install і змушений перебудовувати значну частину дерева —
звідси відчуття, що "install став довше".

Для порівняння: `client` (має бути pnpm) — чистий, жодного npm-маркера
немає. `reviewer-core` і `e2e` (мають бути npm) — теж чисті, жодного
pnpm-файлу. **Тільки `mcp` змішаний.**

### Побічний ефект змішування: дубльований esbuild (~19M)

```
node_modules/.pnpm/@esbuild+darwin-arm64@0.21.5   9.4M
node_modules/.pnpm/@esbuild+darwin-arm64@0.28.2    10M
```

Причина: `tsx` вимагає `esbuild: ~0.28.0`, а `vite` (підтягується
`vitest@2.1.x`) вимагає `esbuild: ^0.21.3` — це два різні, несумісні
діапазони версій у транзитивних залежностях. Це **не наслідок змішування
менеджерів** (сталося б і при чистому npm/pnpm), а звичайний конфлікт версій
у графі залежностей. Прибрати без апгрейду `tsx`/`vitest` до сумісних версій
не вийде — окремо відзначаю, що це не "сміття", а ціна двох різних
tool-chain'ів (tsx для запуску, vite/vitest для тестів) в одному невеликому
пакеті.

### Що з `inspector` — підозріла на вигляд, але нешкідлива залежність

`mcp/package.json` має `"inspector": "^0.5.0"` в `dependencies`. Перевірив:

- Це **не** вбудований Node.js модуль `node:inspector` (той не потребує
  install — просто `import "node:inspector"`), а окремий npm-пакет
  `inspector@0.5.0` ("Node.js binding for WebKit Inspector API", автор
  Admazely, останній realistic maintenance — довкола 2015, залежить від
  `ws@0.7.x` і `endpoint@0.4.x`).
- `grep -rn "inspector"` по `mcp/src` і `mcp/test` — **0 співпадінь**. Пакет
  ніде не імпортується.
- На диску сам він важить 0B (метадані), і `ws@0.7.x`/`endpoint@0.4.x` в
  дереві навіть не встановлені (npm ls не показав жодного споживача крім
  самого `inspector`) — тобто збитку по розміру він практично не завдає.
- Це виглядає як залишок після якогось дебагу (можливо, хтось хотів
  Node-інспектор і випадково поставив однойменний старий npm-пакет), але
  оскільки він 0 байт і ніде не використовується — це не причина
  сповільнення install, просто зайвий рядок у `dependencies`, вартий
  прибирання заради чистоти (`npm uninstall inspector`), а не заради розміру.

## Підсумок / що робити

1. **Головна знахідка:** `mcp/` має одночасно `pnpm-lock.yaml` +
   `pnpm-workspace.yaml` І `package-lock.json`, а `node_modules` зараз
   фізично в pnpm-layout — це суперечить власній конвенції репо (mcp має
   бути npm-only, як `reviewer-core`/`e2e`) і, найімовірніше, є причиною
   того, що `npm install` "став помітно довше" — npm постійно бореться зі
   станом, який лишив pnpm. **Рекомендація:** обрати один менеджер (за
   конвенцією — npm), видалити `mcp/pnpm-lock.yaml` і
   `mcp/pnpm-workspace.yaml`, зробити `rm -rf mcp/node_modules && cd mcp &&
   npm ci` для чистого перевстановлення.
2. `inspector@^0.5.0` в `mcp/package.json` — не використовується в коді
   (перевірено grep'ом), схоже на залишок помилкового `npm install
   inspector` замість вбудованого `node:inspector`. Безпечно прибрати.
3. Дубльований `esbuild` (0.21.5 vs 0.28.2, ~19M) у `mcp` — конфлікт версій
   між `tsx` і `vite`/`vitest`, не пов'язаний з п.1, і не усувається без
   апгрейду залежностей; невелика й очікувана ціна.
4. У `client` (623M) — все перевірено grep'ом, все використовується
   (включно з `mermaid`, який довелось шукати через динамічний `import()`).
   Розмір великий через сам Next.js + mermaid + lucide-react, а не через
   зайвину чи дублі.
5. Версії спільних пакетів (`zod`, `typescript`, `vitest`, `@types/node`)
   ідентичні між усіма п'ятьма пакетами на рівні фактично встановлених
   версій — дрейфу версій між пакетами не виявлено.
